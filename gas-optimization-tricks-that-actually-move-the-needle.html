Gas optimization tricks that actually move the needle

Most gas optimization advice online is either obvious or irrelevant—"use uint256 instead of uint8" doesn't mean much until you understand why and when. After profiling dozens of contracts with Foundry's --gas-report and Hardhat Gas Reporter, these are the changes that consistently shave meaningful gas from real deployments.

Storage Is the Enemy

Cold SLOAD costs 2,100 gas. Warm SLOAD costs 100. Writing to a new storage slot (SSTORE) costs 22,100 gas. Every decision in a hot function should start with "how many storage operations am I doing?" If the answer is more than one per variable, you're leaking gas.

Cache Storage Variables in Memory

This is the single highest-yield change in most contracts. Read a storage variable once, work with the local copy, write back once at the end.

// Expensive: 3 SLOADs
function bad() external {
    require(balance[msg.sender] >= 100);
    balance[msg.sender] -= 100;
    emit Withdrawn(balance[msg.sender]);
}

// Cheap: 1 SLOAD, 1 SSTORE
function good() external {
    uint256 bal = balance[msg.sender]; // cache
    require(bal >= 100);
    bal -= 100;
    balance[msg.sender] = bal;
    emit Withdrawn(bal);
}

Pack Structs Tightly

The EVM stores storage in 32-byte slots. If you arrange struct fields so multiple values share a slot, you pay for fewer slots. Order matters—smaller types grouped together.

// 3 storage slots
struct Wasteful {
    uint256 amount;
    bool active;
    uint256 timestamp;
}

// 2 storage slots
struct Packed {
    uint256 amount;
    uint96 timestamp; // fits with bool in one slot
    bool active;
}

Calldata Over Memory for External Functions

For external functions that receive arrays or structs without modifying them, use calldata instead of memory. memory copies the data; calldata reads it in place.

// Copies array into memory: ~200+ extra gas per element
function processMemory(uint256[] memory ids) external { ... }

// Reads from calldata directly
function processCalldata(uint256[] calldata ids) external { ... }

On a 50-element array, this difference compounds quickly. Profile it yourself with forge test --gas-report and you'll typically see 15–30% savings on the function call.

Short-Circuit with Custom Errors

Replacing require(condition, "long string message") with custom errors saves deployment gas (no string storage) and runtime gas (cheaper revert data).

// Old: stores the string, larger bytecode
require(msg.sender == owner, "Caller is not the owner");

// New: 4-byte selector, no string storage
error Unauthorized(address caller);
if (msg.sender != owner) revert Unauthorized(msg.sender);

This isn't just cleaner—on a contract with twenty access checks, the bytecode reduction matters for deployment cost too.

Unchecked Math Where Safe

Since Solidity 0.8.0, overflow checks are built in. They cost gas. When you can prove overflow is impossible—like decrementing a value you just checked is large enough—wrap the operation in unchecked.

function debit(uint256 amount) external {
    uint256 bal = balance[msg.sender];
    require(bal >= amount);
    unchecked {
        balance[msg.sender] = bal - amount; // safe: checked above
    }
}

Don't scatter unchecked everywhere. Use it surgically, and leave a comment explaining why overflow is impossible. Future auditors will thank you.

Mappings Beat Arrays for Lookups

If you're iterating an array to find an element, you're burning gas proportional to array length. A mapping lookup is O(1) and costs a single SLOAD. The pattern is to maintain both if you need enumeration, but use the mapping for existence checks and data access.

mapping(address => bool) public isWhitelisted;
address[] public whitelistArray; // only for off-chain enumeration

function addToWhitelist(address user) external onlyOwner {
    isWhitelisted[user] = true;
    whitelistArray.push(user);
}

// Fast: one SLOAD
function checkAccess(address user) internal view {
    require(isWhitelisted[user], "Not whitelisted");
}

Immutable and Constant Variables

Variables that never change after deployment shouldn't live in storage. constant embeds the value directly in bytecode. immutable is set in the constructor and also avoids storage reads at runtime.

contract Token {
    uint256 public constant MAX_SUPPLY = 1_000_000e18; // PUSH opcode, no SLOAD
    address public immutable treasury; // set once, read from bytecode

    constructor(address _treasury) {
        treasury = _treasury;
    }
}

Accessing MAX_SUPPLY or treasury costs roughly 3 gas instead of 2,100. Over many calls, this is material.

Measure Everything

None of this replaces profiling. Set up a Foundry gas snapshot baseline before refactoring:

forge snapshot
# make changes
forge snapshot --diff

The diff shows you exactly which functions improved and by how much. Optimization without measurement is guesswork. Write the test, run the snapshot, change one thing at a time, and let the numbers tell you what moved the needle.
