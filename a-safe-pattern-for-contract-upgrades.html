A safe pattern for contract upgrades

Upgrading a deployed contract without bricking user funds is one of the trickier problems in Solidity development. The proxy pattern solves it, but proxies introduce their own failure modes: storage collisions, uninitialized implementations, and accidental selfdestruct calls. This article walks through the UUPS (Universal Upgradeable Proxy Standard) pattern, explains why it's safer than the older Transparent Proxy, and shows you exactly how to wire it up with OpenZeppelin v5.

Why Proxies Work

A proxy contract holds all the storage and ETH, but delegates every call to a separate implementation contract using delegatecall. Because delegatecall executes the implementation's code in the proxy's storage context, users always interact with one stable address while you swap the logic underneath.

// Simplified delegatecall mechanics
fallback() external payable {
    address impl = _getImplementation();
    assembly {
        calldatacopy(0, 0, calldatasize())
        let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch result
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

UUPS vs Transparent Proxy

The classic Transparent Proxy puts upgrade logic inside the proxy itself and uses admin checks to route calls. That means every single user transaction pays extra gas to perform the admin check. UUPS flips this: the upgrade function lives in the implementation, not the proxy. The proxy becomes a thin shell — cheaper to deploy and cheaper per call.

The tradeoff is responsibility. If you deploy an implementation that removes the upgrade function, you're permanently locked. That's why a disciplined upgrade workflow matters more with UUPS than with Transparent Proxy.

Writing a UUPS-Compatible Contract

Install the OpenZeppelin contracts package first:

npm install @openzeppelin/contracts-upgradeable

Here's a minimal upgradeable token contract:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.22;

import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";

contract MyTokenV1 is
    Initializable,
    ERC20Upgradeable,
    OwnableUpgradeable,
    UUPSUpgradeable
{
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    function initialize(address initialOwner) public initializer {
        __ERC20_init("MyToken", "MTK");
        __Ownable_init(initialOwner);
        __UUPSUpgradeable_init();
        _mint(initialOwner, 1_000_000 ether);
    }

    function _authorizeUpgrade(address newImplementation)
        internal
        override
        onlyOwner
    {}
}

Three things to notice:

  • _disableInitializers() in the constructor — prevents anyone from calling initialize on the bare implementation contract and taking ownership before you deploy the proxy.
  • No constructor logic — all setup goes in initialize, which runs exactly once through the proxy.
  • _authorizeUpgrade — this is the gate. Only the owner can push a new implementation. Customize this to a multisig or timelock in production.

Deploying with Hardhat and OpenZeppelin Upgrades Plugin

import { ethers, upgrades } from "hardhat";

async function main() {
  const MyTokenV1 = await ethers.getContractFactory("MyTokenV1");
  const [deployer] = await ethers.getSigners();

  const proxy = await upgrades.deployProxy(MyTokenV1, [deployer.address], {
    kind: "uups",
  });

  await proxy.waitForDeployment();
  console.log("Proxy deployed to:", await proxy.getAddress());
}

main();

The plugin handles deploying the implementation, deploying the ERC1967 proxy, and calling initialize atomically. It also writes a .openzeppelin/ manifest file that tracks your deployment history — commit this to version control.

Performing a Safe Upgrade

When you're ready to ship MyTokenV2, the plugin validates storage layout compatibility before touching the chain:

const MyTokenV2 = await ethers.getContractFactory("MyTokenV2");
const upgraded = await upgrades.upgradeProxy(PROXY_ADDRESS, MyTokenV2, {
  kind: "uups",
});

If MyTokenV2 reorders existing storage slots, the plugin throws before broadcasting any transaction. This catches the most common upgrade foot-gun without requiring you to audit the layout manually.

Storage Layout Rules to Follow

  • Never remove or reorder existing state variables between versions.
  • Only append new variables at the end of the contract.
  • If you use inheritance, the parent chain order must stay the same.
  • Use a storage gap in base contracts you control: uint256[50] private __gap; so future parents can add variables without shifting child storage.

Add a Timelock for Production

Handing _authorizeUpgrade to a plain EOA owner is fine for a testnet, but in production you want a delay between "upgrade proposed" and "upgrade executed." Wire _authorizeUpgrade to OpenZeppelin's TimelockController — a 48-hour delay gives users time to exit if they disagree with an incoming change. Combine that with a multisig (like Safe) as the timelock proposer and you've got a defensible upgrade process that doesn't rely on a single private key.

Quick Checklist Before Upgrading

  • Run upgrades.validateUpgrade in CI against every PR that touches contract code.
  • Deploy the new implementation to a fork of mainnet and run your full test suite against the upgraded proxy.
  • Verify the new implementation on Etherscan before calling upgradeProxy.
  • Confirm the proxy's owner (or timelock) is the account executing the upgrade transaction.
  • Monitor events — Upgraded(address indexed implementation) is emitted by the ERC1967 proxy on every successful upgrade.

Upgradeable contracts are a sharp tool. The UUPS pattern keeps the proxy lean, but it demands that every new implementation is vetted before it goes live. Automate the storage validation, enforce a timelock, and treat each upgrade like a deployment — because for your users, it effectively is one.
