Events vs storage: cheaper ways to track state

Every byte you write to contract storage costs gas. SSTORE on a cold slot runs you 20,000 gas the first time and 2,900 on subsequent writes. Events, on the other hand, cost 375 base gas plus 8 gas per non-zero byte in the log data. That gap is enormous, and it shapes a pattern you'll see in well-optimized contracts: use storage only for data the contract itself needs to read on-chain, and push everything else into events for off-chain consumers.

What each mechanism actually does

Storage variables live in the contract's persistent state trie. Any function—including other contracts—can read them via SLOAD. Events are emitted via LOG opcodes and written into the transaction receipt. The EVM never reads them back; they exist purely for the outside world.

That distinction drives the decision. If your contract needs to check a value during execution, it must be in storage. If only your frontend, indexer, or analytics pipeline needs it, an event is almost always the right call.

A concrete example: tracking deposit history

Imagine a simple vault. A naïve implementation might store every deposit in a mapping or array:

// Expensive approach
mapping(address => uint256[]) public depositHistory;

function deposit() external payable {
    depositHistory[msg.sender].push(msg.value);
}

Each push writes a new storage slot: 20,000 gas for the first deposit per user, plus pointer updates to the dynamic array. For a busy vault this balloons quickly.

If your UI just wants to display a user's past deposits, you don't need that data on-chain. Replace the array with an event:

event Deposited(address indexed user, uint256 amount, uint256 timestamp);

function deposit() external payable {
    emit Deposited(msg.sender, msg.value, block.timestamp);
}

The gas drop is dramatic. A cold SSTORE becomes a LOG2 (two indexed topics). Your frontend queries deposits with eth_getLogs filtered by the user topic. An indexer like The Graph or a simple ethers.js listener reconstructs the full history off-chain.

Indexed vs non-indexed topics

Events let you mark up to three parameters as indexed. Indexed params are stored as Bloom-filter-searchable topics; non-indexed params go into the ABI-encoded data field. Use indexed for fields you'll filter on:

event Transfer(
    address indexed from,   // filterable
    address indexed to,     // filterable
    uint256 amount          // in data blob, cheaper
);

Indexed topics cost a little more than data bytes, so don't over-index. A good rule: index addresses and IDs you'll query by; leave large payloads (strings, byte arrays) in data.

When you genuinely need storage

Events are not a universal replacement. Keep things in storage when:

  • The contract logic reads the value (balances, allowances, access control roles).
  • You need atomic reads inside a transaction (e.g., reentrancy guards, price oracles).
  • Another contract calls a getter on your data.

A token's balance mapping must be in storage because transfer reads and writes it in the same call. The Transfer event is emitted in addition, not instead.

Hybrid patterns worth knowing

Sparse storage + events

Store only the minimal on-chain state and emit rich context as events. An NFT contract stores ownerOf but emits metadata-change events so marketplaces can update listings without any additional storage writes.

Event-sourced state reconstruction

Some protocols (early Uniswap analytics, many L2 bridges) store almost nothing on-chain. A trusted indexer replays all events from genesis to reconstruct current state. This works well when read latency is acceptable and you control the indexing layer.

Packing storage slots

When you do need storage, pack variables into 32-byte slots. Solidity does this automatically for consecutive small types:

// Fits in one slot (8 + 8 + 16 = 32 bytes)
uint64 public lastUpdated;
uint64 public counter;
uint128 public accumulatedFees;

Combine packing with events and you can often cut storage writes by 50–70% on complex state machines.

Tooling to validate your choices

Don't guess—measure. Run forge test --gas-report to see per-function gas usage. Compare the storage-heavy version against the event-based version in the same test suite. You'll usually see a 5–10× difference in gas for write-heavy flows. Cast is handy for quick checks too:

cast estimate <CONTRACT> "deposit()" --value 1ether --rpc-url $RPC

Profile before optimizing, then profile again after. Gas costs can shift with compiler versions and optimizer runs, so keep the benchmarks in CI.

The bottom line

Ask yourself one question for each piece of state: does the contract need this value during execution? If yes, it goes in storage. If only off-chain consumers need it, emit an event. That single habit—applied consistently—can cut your contract's gas footprint significantly without touching business logic. Events are first-class data in the Ethereum ecosystem; treat them that way.
